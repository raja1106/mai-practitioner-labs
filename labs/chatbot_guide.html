Reading chatbot.py

A guided tour of labs/chatbot.py — a ~200-line terminal chatbot with streaming, observability, local classification, and a durable structured user profile.

How to read this file (and most Python programs): don't read top to bottom. Read the docstring first (the author's map), then jump to main() and follow one message through the loop, and only then visit each helper function when the loop calls it. 1 · The docstring is the map lines 1–37

The file opens with a long docstring. It is not decoration — it names the four ideas the file demonstrates, in the order they were added:

IdeaOne sentenceLives in
The loopRead a line, append to history, send the whole history, stream the answer, repeat.main()
ObservabilityEvery request appends one JSON record to traces.jsonl — latency, tokens, ok/error.traces.py
ClassificationA local HuggingFace model tags each message (code generation · sales · design · non-work). Free, offline.hf_classifier.py
Durable memoryA small extraction call distills each message into a structured profile — identity · work · preferences · interests — in profile.json; the profile rides in the system prompt.user_profile.py

Key insight hiding in plain sight: "send the WHOLE history". The model has no memory between API calls — every turn resends everything. That is why token counts grow each turn, and why the profile (a few dozen tokens, constant size) is the token-efficient way to remember things across sessions.

3 · The life of one message

Everything in this file exists to serve this pipeline. One user message flows through eight steps:

input() you type a line — commands starting with / short-circuit here
↓
history.append your message joins the conversation — role: "user"
↓
stream_chat() the WHOLE history goes to the model; the reply streams back word by word API call · label "chatbot"
↓
measure latency from the wall clock, this turn's tokens from meter deltas
↓
classify() the LOCAL model tags your message free · offline
↓
trace() one JSON line into traces.jsonl — the observability record
↓
history.append the reply joins the conversation — role: "assistant"
↓
extract_profile() durable facts → clean() → merged into profile.json, system prompt refreshed API call · label "memory"

Note there are two API calls per turn: the visible reply and the small profile extraction. Both are metered separately — type /cost and you'll see two rows.

5 · The command dispatch lines 124–161

Inside the loop, slash-commands are checked before anything is sent to the model. Each one is a continue — handle it locally, go read the next line. Nothing here costs tokens.

CommandWhat it doesTouches
/costPrint the running meter (calls · tokens, by label)RAM only
/logShow the last 3 trace records, raw JSONreads traces.jsonl
/facts · /profileShow the profile the bot carries, as one lineRAM only
/resetClear the conversation — the profile survives (fresh history still contains it)RAM only
/forgetDelete profile.json, blank the profile, rebuild the system prompt: "we've never met"deletes profile.json
/quitLeave (also q, exit, Ctrl-D, Ctrl-C)—

Notice the deliberate split: /reset is "start a new conversation with someone I know"; /forget is "erase what you know about me". Short-term and long-term memory are separate things with separate controls.

6 · The core turn lines 163–197

Send, and measure around the call

history.append({"role": "user", "content": user})
p0, c0 = meter.prompt_tokens, meter.completion_tokens   # meter snapshot BEFORE…
t0 = time.perf_counter()
reply = stream_chat(cli, history, label="chatbot", on_delta=type_out)
# …AFTER: this turn's cost is the difference
pt, ct = meter.prompt_tokens - p0, meter.completion_tokens - c0

The meter is a session-wide running total, so per-turn numbers come from before/after deltas — a pattern worth stealing. on_delta=type_out is a callback: every streamed fragment is handed to type_out() the moment it arrives, which is what makes the reply appear word by word.

The error path is a feature lines 168–177

except Exception as e:
    history.pop()          # don't resend the turn that failed
    trace(turn=turn, ok=False, error=type(e).__name__, …)
    say("call failed — try again")
    continue               # the chat survives

Three honest moves: undo the append (so a failed message isn't silently resent forever), log the failure as a first-class trace record (ok: false), and keep the loop alive. Compare with the success path's trace — same shape, so the log analyzes cleanly.

7 · The profile memory, up close lines 53–86 + user_profile.py

The lineage — three versions of the same idea, all still on disk:
v1 memory.jsonl — replay the whole transcript. Faithful, but the token bill grows forever.
v2 memory.json — flat key: value facts. Cheap, but flat: a second project invents project_2, and nothing says which keys belong together.
v3 profile.json — give memory a shape. The extractor fills a form instead of inventing structure.

The schema is the contract

SectionHoldsTypeMerge rule
identitywho you are — name, location…key → valuesame key, new value wins
workwhat you do — role, company, current_project…key → valuesame key, new value wins
preferenceshow you want answers — response_style…key → valuesame key, new value wins
interestswhat you're intolist of stringsappend, case-insensitive dedupe

So a promotion updates work.role in place (the file doesn't grow), while a new hobby appends to interests (and mentioning python twice doesn't store it twice).

The extraction prompt is where the policy lives

EXTRACT = (
    "You maintain a long-term user profile for a chatbot. From the user's "
    "message, extract only DURABLE facts — things still true next week. "
    "Reply with ONLY JSON in this exact shape, every section optional: "
    '{"identity": {"name": "..", "location": ".."}, '
    '"work": {"role": "..", "company": "..", "current_project": ".."}, '
    '"preferences": {"response_style": ".."}, '
    '"interests": ["short topic", ".."]}. '
    "Short snake_case keys, short values; {} if nothing durable. Report only "
    "what is new or changed vs the current profile: "
)

Every design decision is in that prompt: durable only ("still true next week" — so "I'm hungry" is not stored), a form to fill (the exact JSON shape, so facts land in the right section under stable keys instead of inventing new ones), compact (this text rides in every future system prompt), and incremental (only new/changed facts — the current profile is appended to the prompt so the model reuses existing keys and reports deltas).

Trust nothing: the defensive layers

def extract_profile(cli, profile, user):
    try:
        raw = chat(cli, […], label="memory", max_tokens=200)
        start, end = raw.find("{"), raw.rfind("}")   # tolerate prose/code fences
        new = json.loads(raw[start:end + 1]) if start != -1 else {}
        return clean(new)                            # schema-check it — the extractor is an LLM
    except Exception:
        return {}                                    # memory must never break the chat

Because LLMs don't always return clean JSON: slice from the first { to the last } (survives ```json fences and chatty preambles), pass the result through clean() (unknown sections, nested junk, and empty values never reach the file), and catch everything — a memory hiccup costs you one fact, never the conversation. max_tokens=200 caps the spend, and label="memory" gives it its own row in /cost.

8 · The small helpers lines 89–106

classify() wraps the local HF model in the same "telemetry must not break the app" try/except. Returns None on any failure; the loop checks for that.

type_out() is the typewriter effect: split each streamed fragment on whitespace (re.split(r"(\s+)", …) — the capture group keeps the whitespace so spacing is preserved), print each word, sleep 40 ms. Because it works per fragment, it looks right whether the proxy streams many small deltas or falls back to one big one.

And the conversation itself — history — is deliberately not on disk. It's a Python list in RAM that dies with the process. Only the distilled profile survives.

10 · The design principles

1 · Glass-box. Every moving part is a short file you can open. No framework.
2 · Honest degradation. No classifier? Chat works, traces go untagged. Stream fails? Retry unstreamed, tell the user. Profile extraction chokes? Return {}. Side-features are wrapped so the core loop never dies for a side reason.
3 · Cost is visible, always. The meter, per-turn token lines, memory's own /cost row. If a feature costs tokens, you can see exactly how many.
4 · Observability is append-only JSON. One line per request, errors included, analyzed later with standard tools.
5 · Memory = distillation into a schema. Store what will still be true next week, in a shape that merges predictably and costs a constant handful of tokens.
6 · Validate at the boundary. The LLM proposes, clean() disposes — nothing an LLM generates is written to disk unchecked.

11 · Things to try

  • Run it (python labs/chatbot.py), tell it your name, /quit, run it again, ask "what's my name?" — the durability test.
  • Tell it about a promotion or a move — watch work.role or identity.location update in place (same key, new value) instead of growing the file.
  • Mention a hobby twice in different sessions — interests should store it once (the dedupe).
  • Tell it something ephemeral ("I'm tired today") — the extractor should store nothing.
  • Type /cost and compare the chatbot row to the memory row — what does remembering cost?
  • cat labs/profile.json and python labs/user_profile.py — read the profile both raw and pretty-printed.
  • Watch the (tokens: …) line climb turn by turn in one session — that's "send the WHOLE history" made visible. Then /reset and watch it drop back while the bot still knows you.
  • Break it on purpose: turn off Wi-Fi mid-chat and watch the error path do its three honest moves.
