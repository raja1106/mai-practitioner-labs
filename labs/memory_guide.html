The three memories of chatbot.py

Working · episodic · durable — how a 350-line lab chatbot remembers the present, the past, and the permanent. Companion to the line-by-line guide.

The idea in one paragraph. An LLM has no memory at all — every API call starts blank, so whatever the bot should "remember" must be packed into the prompt, and tokens cost money. The answer isn't one memory, it's three, each with a different lifetime and a different price: the working memory is the conversation happening right now (full fidelity, grows every turn); episodic memory is whole past conversations filed by theme (full transcripts on disk, but only pointers in the prompt); and durable memory is the distilled user profile (a few dozen tokens, always present). This mirrors how human memory is usually described — and it falls out naturally from asking "what deserves prompt space every turn?"

1 · The three memories at a glance

Working

labs/memory.jsonl + history in RAM

Holds: the current episode's turns, verbatim.

Lives: until you switch episodes (buffer survives restarts).

Prompt cost: grows every turn — full transcript resent.

Episodic

labs/episodes/<id>-<slug>.json

Holds: whole past conversations — transcript + last-state summary.

Lives: forever, one file per theme; resumable.

Prompt cost: constant — only [id] title: summary pointers ride along.

Durable

labs/profile.json

Holds: invariant facts — identity · work · preferences · interests.

Lives: forever, updated in place as facts change.

Prompt cost: constant — one compact sentence.

All three meet in the system prompt, which system_msg() assembles fresh whenever any of them changes:

"You are a friendly, concise assistant…                                ← personality
 Known about this user from earlier chats: identity — name: Raja ·
 location: Bangalore; work — role: senior data engineer; …            ← durable
 Recent episodes (other conversations you two had): [001] Focus Help:
 …; [002] Goa trip planning: …; [003] Python decorators: …            ← episodic pointers
 The current conversation's theme: Goa trip planning."                 ← working context

2 · The life of one turn (now three API calls)

detect_topic() from the 2nd message on: does this continue the current theme? API call · "episodes" · ~80 tok
↓ topic changed? → the bot ASKS; saying y runs the episode switch (next section) first
stream_chat() the whole working history goes to the model; the reply streams back API call · "chatbot"
↓
trace() + token line latency, per-turn cost, classifier tag — the observability layer
↓
working_append() ×2 user + reply appended to memory.jsonl — only turns that succeeded
↓
extract_profile() durable facts distilled into profile.json API call · "memory" · ≤200 tok

Every call has its own label, so /cost itemizes the bill. From a real test session: episodes ×5 (1843 tok) · chatbot ×3 (2746 tok) · memory ×3 (757 tok) — the remembering machinery cost roughly half as much as the talking.

3 · The episode switch, step by step

This is the new machinery. The rule: the bot never switches on its own — it asks. Topic detection is a judgment call by a small model; the user stays in charge.

1 · detect detect_topic() returns {topic, same_episode, matches_episode} — it sees the current theme and the shelf pointers, so it can recognize a return to an old episode
↓ same_episode: false
2 · ask (new topic: Python decorators — file this chat and start a new episode? [y/N]) — N means "false alarm, carry on"
↓ y
3 · file file_working_episode(): one wrap-up call writes a last-state summary + title, then the whole buffer moves to episodes/<id>-<slug>.json API call · "episodes" · ≤200 tok
↓
4a · resume if the new topic matches a shelved episode, its transcript reloads into history + buffer — the conversation continues where it left off
4b · fresh otherwise the buffer restarts empty, titled by the detected topic
↓
5 · reply the message that triggered the switch is answered inside the new episode

What it looks like — a real transcript

From the test run (episode 002 already held a 4-message Goa plan):

you > explain python decorators in two sentences with one tiny example
    (new topic: Python decorators explanation — file this chat and start a new episode? [y/N]) > y
    (filed [002] Goa trip planning)
bot > A decorator is a function that wraps another function to add behavior…

you > ok back to my goa trip plans please
    (new topic: Goa trip planning — file this chat and resume [002] Goa trip planning? [y/N]) > y
    (filed [003] Python decorators explanation)
    (resumed [002] Goa trip planning — The trip was refined into a quiet, 3-day
     December Goa itinerary focused on beaches and seafood, avoiding parties…)
bot > Sure — continuing with the relaxed December Goa plan…

you > how many days was I planning to stay and in which month?
bot > You were planning a 3-day trip in December.

That last exchange is the whole point: the December detail came back because the transcript came back — episodic memory restores full fidelity, not just a summary.

4 · The working buffer: one file, three tricks episodes.py

labs/memory.jsonl is append-only JSONL, one message per line — plus one special line:

{"ts": "…", "episode": "002", "title": "Goa trip planning"}   ← the header: whose buffer is this?
{"ts": "…", "role": "user", "content": "let's plan my goa trip…"}
{"ts": "…", "role": "assistant", "content": "Great choice—December…"}

Trick 1 — crash-proof: every successful turn is appended immediately, so killing the process loses nothing; startup replays the buffer and you resume mid-conversation.
Trick 2 — the header line: records with an "episode" key instead of a "role" are metadata, skipped by working_messages(); the last one wins, so re-filing is just appending.
Trick 3 — the buffer IS the unit of filing: "move working memory into the episode" is literally: summarize the buffer, write it to the shelf, restart the buffer.

6 · The two new prompts chatbot.py 81–95

TOPIC (the detector, ≤80 tokens out) — sees the current theme and the shelf pointers, returns {"topic", "same_episode", "matches_episode"}. Its judgment is deliberately cheap and deliberately advisory: a false positive costs the user one keystroke (N), a false negative costs nothing (the /switch command still exists).

WRAP (the archivist, ≤200 tokens out) — writes the last-state summary at filing time: what was discussed, what was decided, what threads are still open. That summary then does double duty: it's the episode's label on the shelf, and it's what the next system prompt shows as a pointer.

Both wrap their JSON parsing in the same armor as the profile extractor: slice {…} out of whatever came back, validate, and on any failure return "do nothing" — memory machinery must never break the conversation.

8 · Design lessons worth stealing

1 · Ask before switching. Topic detection is probabilistic; context loss is expensive. The cheap direction (ask, one keystroke) absorbs the errors of the expensive one.
2 · Summaries for awareness, transcripts for fidelity. Pointers keep every past episode one sentence away; resuming restores the full text. Don't make the prompt pay for fidelity it doesn't need yet.
3 · The buffer is the unit of work. One append-only file that is resumed, filed, and restarted — no state machine, no database, readable with cat.
4 · Failure means "do nothing", never "break". Detector down? No interruption. Wrap-up failed? File with a placeholder summary. The chat always survives its memory.
5 · Every memory has a price tag. Three meter labels — chatbot, episodes, memory — so you can answer "what does remembering cost?" with a number.

9 · Things to try

  • Chat about one thing, then abruptly ask about another — watch the ask. Say N and notice nothing was lost.
  • Say y, chat a while, then say "let's get back to <old topic>" — watch it offer the resume, and quiz the bot on a detail from the old conversation.
  • Kill the terminal mid-conversation and restart — the working buffer resumes exactly where you were.
  • cat labs/memory.jsonl — find the header line. cat labs/episodes/002-*.json — find the summary and the transcript.
  • /cost after a switch-heavy session — compare the three rows. Is episodic memory worth its tokens to you?
  • Watch the prompt-token number jump when you resume a long episode — fidelity has a price, and now you can see it.
